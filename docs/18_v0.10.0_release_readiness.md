# v0.10.0 Release Readiness

## Product

**Quant Research Workbench 1.0** provides a local, five-page Streamlit research
workflow over the existing canonical pipeline and Artifact contracts.

Pages:

- Overview
- New Run
- Results
- Runs
- Data

The verified user flow is:

```text
New Run
  -> canonical PipelineConfig
  -> existing Modeling / ML / Signal / Holdings / Research Backtest pipeline
  -> exact Artifact-backed Results
  -> Runs catalog
  -> reopen the exact selected run
  -> read-only Data status
```

## Frozen UI principles

- The GUI is a controller and viewer; it does not own quant calculations.
- New Run produces only the canonical `PipelineConfig` schema and calls the
  existing pipeline path.
- Results reads validator-backed canonical Artifacts for one exact `run_id`.
- Canonical finance metrics come directly from Research Backtest
  `metrics.json` and are not recomputed by the GUI.
- Run selection has no latest, filesystem-mtime, glob, nearest, prefix, fuzzy,
  or cross-run fallback.
- Holdings keeps canonical identity, rank order, selection, and zero-weight
  rows.
- Data is read-only and performs no provider call, download, refresh, repair,
  cache write, Parquet write, or full data-lake scan.
- Historical failure status, stage, reason, and timestamp are shown only when
  canonical metadata exists. The current runner may leave an exact run
  directory without `run_info.json` when it fails before normal persistence;
  the catalog does not invent those fields.
- Risk Model, optimizer, Factor, ML, Signal, Holdings, Research Backtest, Data
  provider, pipeline stage, and Artifact schema semantics are unchanged.

## Results contract

- Metric cards use all 20 exact Research Backtest metrics.
- Portfolio NAV uses `daily_portfolio.parquet.net_nav`.
- Benchmark NAV uses `benchmark.parquet.benchmark_nav`, with exact one-to-one
  Artifact date alignment and no fill or interpolation.
- Drawdown is derived only for chart display. A mismatch warns and never
  replaces canonical `net_max_drawdown`.
- Holdings comes from exact `holdings.parquet`, including zero-weight selected
  rows.
- Daily returns use canonical accounting columns. Monthly returns are clearly
  marked display-only and compound daily `net_return` as
  `product(1 + return) - 1`.
- Config comes from the exact run's `config_snapshot.yaml`, not current form or
  session draft state.
- Artifact identity, safe relative paths, schema versions, validation status,
  and recorded ML -> Signal -> Holdings -> Research Backtest lineage are shown
  only when present and valid.
- Missing Research Backtest remains a friendly unavailable state while valid
  Holdings, Config, and earlier lineage remain readable.
- Missing files, corruption, negative Holdings weights, wrong schema version,
  and broken integrity fail closed through existing validators.

## Exact-run and catalog proof

The P3 E2E generated two clearly distinct runs through the real offline
Modeling -> ML -> Signal -> Holdings -> Research Backtest path. Each Results
load retained its own metrics, NAV, config snapshot, ML experiment identity,
and lineage; no cross-contamination was observed.

Identity gates reject nonexistent, malformed, traversal, absolute, nested,
file, symlink (when supported by the host), nearest, and prefix identities.
Run enumeration includes only valid direct child directories. Canonical
`run_info.json.created_at` is the sole chronological truth. Runs without it use
stable run-ID order and cannot become Latest through mtime or lexical inference.

## Current-session failure behavior

A deterministic post-run-creation failure was exercised through `RunService`.
It returned `success=False`, preserved the exact callback-created run identity,
provided safe diagnostic details, and did not change `selected_run_id` or route
to fake Results. Because no canonical `run_info.json` was persisted, the
historical catalog kept status and created time as `N/A` and did not invent a
failed stage or reason.

## Non-goals

v0.10.0 does not add run comparison, deletion, rename, favorites, tags,
duplication, asynchronous jobs, a database, login, multi-user behavior, cloud
sync, data-update UI, live trading, new quant methods, or persistent historical
failed-run diagnostics.

compile/import, protected-diff, exact-identity, Artifact validation, and
read-only Data conditions passed with no blocker.
