# v0.6.0 Release Readiness

> Release-candidate verification for the V5 Signal/Holdings feature branch.
> This document does not claim that v0.6.0 has been merged, tagged, pushed, or
> released.

## 1. Release scope

V5 extends the existing offline research pipeline with deterministic Signal
and long-only equal-weight Holdings stages. V5-F adds no production behavior;
it verifies the completed implementation with offline end-to-end tests.

## 2. Architecture

The canonical dependency direction is:

```text
UI or YAML
  -> PipelineConfig
  -> Data readiness
  -> Factor Research (optional)
  -> Modeling Panel (optional)
  -> ML Experiment / native ML Artifact
  -> Signal Artifact
  -> Holdings Artifact
  -> Runner summary + config snapshot
```

Runner handoffs use only explicit results from the current run. Files mode is
the sole exception: it consumes one explicitly configured and validated native
ML Artifact directory.

## 3. V5 stage map

- ML produces walk-forward out-of-sample predictions and, when required by
  Signal `ml` mode, publishes the native ML Artifact.
- Signal validates that Artifact, maps `prediction` to `score`, and assigns a
  deterministic per-date rank.
- Holdings consumes the exact Signal Result/Artifact, selects existing ranks
  `<= holdings.top_n`, and assigns equal target weights.
- The Runner coordinates stages but does not read Parquet, rank, select, or
  calculate weights.

## 4. User-facing capabilities

Users can enable Signal/Holdings through canonical YAML or the minimal
Streamlit bridge, choose Top N, choose high-score-first or low-score-first, and
choose strict error or allow-partial behavior for small universes. V5 weighting
is intentionally fixed to equal weight.

## 5. Config source of truth

`PipelineConfig` is the only canonical pipeline configuration. The V5 business
owner of selection count is `HoldingsPipelineConfig.top_n`; its backend default
is 20. Signal direction and insufficient-universe policy use the validated
nested Signal/Holdings configs. Builders receive explicit values and define no
second business defaults.

## 6. Top-N semantics

Top N is applied independently per `trade_date` to existing Signal ranks. It
does not change predictions, scores, or ranks. Real same-source runs at N=5,
10, and 20 proved identical Signal payloads, exact holdings counts, weights of
1/5, 1/10, and 1/20, and the prefix invariant Top5 < Top10 < Top20.

The example YAML's value 10 is a user example, not a backend default.

## 7. UI bridge

The Streamlit V5 action loads one explicit direct-schema YAML, builds a detached
effective config, validates it through `PipelineConfig.from_dict`, and invokes
the in-process canonical `run_pipeline(config)` service. Its Top N default is
read from `HoldingsPipelineConfig().top_n`; it has no V5 hardcoded 10 and no
maximum-100 contract. Direction and insufficient-universe labels map to backend
enums, and equal weight is read-only.

The pre-run display comes from the effective config. Post-run paths and counts
come from the Runner summary. UI code does not read Parquet, rank, select, or
calculate weights. The older research/backtest subprocess controls remain in a
separately labeled legacy section.

## 8. Legacy root `top_n` compatibility mirror

The root `PipelineConfig.top_n` is retained for v0.5.0-era workflows. When
Holdings is enabled, current config validation requires it to equal nested
`holdings.top_n`. The UI bridge therefore performs a one-way compatibility
mirror:

```text
validated UI value -> holdings.top_n -> derived legacy root top_n
```

The root value never overrides the nested value. Runner, Holdings Executor,
Builder, Artifact, summary, and user display read the nested configuration.
Conflicting independently supplied root/nested values are rejected. There is
one UI widget and one V5 backend default.

This mirror is compatibility debt. A later version may remove it after the
legacy root field and old workflows have a deliberate migration path; v0.6.0
must not remove that field and break backward compatibility immediately before
release.

## 9. Signal contract

Signal schema 1.0 is exactly `trade_date, ts_code, score, rank`. Output excludes
`target`, `y_true`, `fold_id`, Top-N, selected flags, and weights. The score
source cannot be a protected label, key, audit, rank, or portfolio column.

## 10. Holdings contract

Holdings schema 1.0 is exactly `trade_date, ts_code, target_weight, score,
rank`. Holdings preserves Signal score/rank and does not recalculate either.
It is long-only, unlevered, and supports only `equal_weight`.

## 11. OOS guarantee

The native ML Artifact contains predictions produced by the existing
walk-forward OOS training path. Signal accepts only:

- the current run's enabled ML Result with a validated, persisted native ML
  Artifact; or
- an explicitly configured files-mode native ML Artifact directory.

The fixed native prediction schema includes OOS audit fields, but Signal emits
only keys, score, and rank. A bare `predictions.parquet`, generic external
Parquet, tampered Artifact, train-prediction guess, validation-prediction guess,
latest scan, or prior-run fallback cannot satisfy the source adapter.

The release audit is backed by ML walk-forward tests, ML Artifact validation,
`tests/test_signal_sources.py`, Signal contract/builder tests, and the V5-F real
Runner E2E.

## 12. Deterministic ranking

`descending` ranks larger score first; `ascending` ranks smaller score first.
Ties use `ts_code` ascending. Stable mergesort and per-date contiguous ranks
make results invariant to shuffled input. Release E2E verifies both directions,
ties, shuffled input, date isolation, and ranks 1..N.

## 13. Insufficient universe

- `error`: any date with fewer than requested N fails the complete Holdings
  stage. The valid Signal Artifact remains, no Holdings Artifact or success
  snapshot is fabricated.
- `allow_partial`: a short date selects its actual K, records that date in
  audit, retains requested N in config, and assigns 1/K weights.

The V5-F mixed-universe E2E includes both normal and partial dates.

## 14. Equal weight

Every selected row has a finite, strictly positive target weight. Per-date
weights sum to one within the fixed absolute tolerance. Normal dates use 1/N;
allow-partial dates use 1/K. No short position or leverage is introduced.

## 15. Artifact integrity

Signal and Holdings each publish exactly four files: one Parquet payload,
`config.json`, `audit.json`, and `manifest.json`. Stores verify schema, dtypes,
row order, business semantics, file sizes, SHA-256 hashes, and cross-file
consistency. Publication uses same-parent staging, manifest-last construction,
atomic directory replacement, strict no-overwrite, and staging cleanup.

Tamper tests cover payload and metadata corruption. V5-F additionally proves
tampered native ML blocks Signal and tampered Signal blocks Holdings.

## 16. Lineage

Lineage is deliberately chained rather than flattened:

```text
Holdings manifest
  -> exact Signal Artifact path + signals.parquet SHA + Signal schema
Signal manifest
  -> exact ML Artifact path + predictions SHA + ML schema
     + experiment ID + model identity
```

Holdings does not duplicate all ML metadata. The two direct provenance links
are sufficient to trace Holdings -> Signal -> ML.

## 17. Runner handoff and run isolation

Current-run ML Result is passed directly to Signal `ml` mode; current-run
Signal Result is passed directly to Holdings. Different executions create
different run directories and stage paths. Same-source repeated runs produce
identical Signal and Holdings business payloads after excluding runtime paths
and timestamps. A newer sibling Artifact does not affect an explicit files
source.

## 18. CLI and YAML

The canonical command remains:

```powershell
python scripts/run_pipeline.py --config config/signal_holdings_pipeline.example.yaml
```

The example parses through the formal loader and enables Modeling Panel, ML,
Signal, and Holdings. No Signal/Holdings-specific CLI flags were added. The
existing `--top-n` is explicitly described as a legacy root-workflow override
and cannot override nested V5 Holdings without triggering conflict validation.
CLI compact and human summaries retain Signal/Holdings paths and effective
business settings.

## 19. Backward compatibility

| Case | Expected result | Verified |
| --- | --- | --- |
| Signal=false, Holdings=false | v0.5.0-style behavior; no V5 summary/stages | Yes |
| Signal=true, Holdings=false | Signal-only | Yes |
| Signal=true, Holdings=true | Full V5 | Yes |
| files source, ML disabled | Valid | Yes |
| ml source, ML disabled | Config invalid | Yes |
| Holdings=true, Signal=false | Config invalid | Yes |
| Old direct YAML | Parses with V5 disabled defaults | Yes |
| Old grouped YAML | Parses with V5 disabled defaults | Yes |

Existing V3 ML-only and V4 Modeling Panel/ML regression suites remain green.

## 20. Failure semantics

- Signal source/build/write failure blocks Holdings.
- Holdings failure preserves the valid upstream Signal Artifact.
- Pre-existing Signal or Holdings targets are not modified.
- Strict insufficient-universe failure leaves Signal valid and Holdings absent.
- Tampered sources are rejected before downstream publication.
- Final config snapshot/run-success metadata is not written after stage failure.

## 21. Run isolation and no-latest rule

The V5 source adapter, Runner, executors, and UI service perform no mtime,
latest, sibling, glob, or recursive source discovery. The only production
`rglob` scan found in the audit is internal validation of entries inside an
already explicit native ML Artifact directory; it is not Artifact selection.
Dashboard uses of “latest” concern display data and are outside the canonical
V5 source path.

## 22. Test matrix

The new `tests/test_signal_holdings_end_to_end.py` has 12 release-level tests:

- real Modeling Panel -> Ridge ML -> native ML Artifact -> Signal -> Holdings;
- explicit files mode and newer-sibling isolation;
- Top-N 5/10/20 trace, weights, prefixes, and same-source Signal invariance;
- UI bridge -> canonical service -> Runner -> Artifacts;
- mixed-universe `error` and `allow_partial`;
- Signal/Holdings no-overwrite preservation;
- tampered ML and tampered Signal rejection;
- deterministic repeated runs and chained lineage;
- deterministic direction/tie/shuffle contract;
- V3/V4 and dependency compatibility matrix;
- one-way UI compatibility mirror and no-discovery static checks.

Existing focused suites continue to cover atomic failure injection, manifest
ordering, all validator tamper variants, time-safety, and lower-level contracts.

## 25. Non-goals

V5 does not implement transaction costs, turnover, PnL backtesting, benchmark
comparison, optimization, score weighting, risk parity, long-short portfolios,
sector neutrality, live trading, generic external prediction Parquet, or
classification-probability semantics.

## 26. Version source and compatibility debt

The repository has no canonical package/version file (`pyproject.toml`,
`setup.py`, `setup.cfg`, or VERSION). Release version is expressed by Git tag.
The current describe value during V5-F is `v0.5.0-8-g295e736`; local tag
`v0.5.0` exists and `v0.6.0` does not. V5-F does not create or modify tags.

Known compatibility debt is the legacy root `top_n` field and the UI bridge's
one-way mirror described above. It is documented and tested, not a release
blocker for backward-compatible v0.6.0.
